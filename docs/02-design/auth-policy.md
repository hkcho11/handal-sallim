# 한달살림 MVP 인증·계정 복구 정책 초안

> 상태: Implemented — 이메일·비밀번호 가입·확인·복구·세션 구현. 초대·외부 로그인은 후속 범위
>
> 기준: `SERVICE_PLAN.md` 0.8, `docs/01-plan/schema.md`
>
> 범위: 가입·로그인, 세션, 초대 수락 시 사용자 식별, 로그아웃, 계정 접근 복구

## 2026-10-28 확정 변경: 앱 안에서 인증번호 확인 뒤 비밀번호 설정

- 가입 화면은 표시 이름·이메일만 받는다. 공개 가입·재가입 요청은 비밀번호를 설정하거나 교체할 수 없다.
- 가입·비밀번호 재설정 메일에는 링크 대신 숫자 8자리 인증번호를 보낸다. 사용자는 요청한 원래 화면에서 번호를 입력하고, 확인 후 비밀번호·확인을 입력해 가입 또는 재설정을 완료한다.
- 번호는 요청 ID·사용자·목적에 연결되며 10분·일회용이다. 잘못 입력하면 5회까지만 허용하며 오류 응답이어도 시도 횟수를 보존한다. 재발급은 이전 번호와 미사용 비밀번호 설정 권한을 폐기한다. 발송 실패 시 이전 번호는 유지한다.
- 번호 확인 후 발급하는 비밀번호 설정 권한도 10분·일회용이며 로그인 권한은 없다. 브라우저 메모리에서만 사용하고 URL·지속 저장소에 저장하지 않는다. 비밀번호 검증 실패는 이 권한을 소모하지 않는다.
- 원래 탭의 sessionStorage에는 요청 ID·이메일 초안·진행 단계만 임시 보관해 번호 입력 중 새로고침에 대응한다. 번호·비밀번호·설정 권한·세션 ID는 보관하지 않는다. 비밀번호 단계에서 페이지가 다시 로드되면 새 번호를 받도록 안내한다.
- 아이폰 홈 화면 웹 앱을 다시 열어 원래 화면에서 번호를 입력한다. Safari로 이동하거나 로그인 쿠키를 브라우저 간 전달하지 않는다. 로그인 화면에서도 진행 중인 인증으로 돌아갈 수 있다.
- 기존 인증 완료 사용자의 비밀번호·세션·금융 기록을 유지한다. 이미 발송된 구버전 링크는 원래 만료까지 수용하고, 새 번호를 요청하면 기존 링크도 폐기한다. 실제 서비스는 HTTPS로 제공한다.

## 1. 이번에 결정할 내용

제품 데이터는 서버의 사용자·공간 멤버십을 기준으로 보호한다. 사용자는 MVP에 자체 이메일·비밀번호 로그인을 선택했다. 가입 확인, 비밀번호 재설정과 세션의 세부 값은 아래 추천안으로 검토한다.

| 선택지 | 장점 | 주의할 점 |
|---|---|---|
| A. 자체 이메일·비밀번호 (선택됨) | 재로그인 시 이메일을 기다리지 않고, Google 계정도 필요 없음 | 비밀번호 안전 저장, 가입 확인, 분실 시 재설정 메일과 로그인 남용 방지가 필요함 |
| B. 이메일 일회용 로그인 링크 | 앱 비밀번호와 재설정 화면이 필요 없음 | 세션이 끝나 재로그인할 때마다 메일을 받아야 함 |
| C. Google 로그인만 제공 | 자체 비밀번호와 재설정 메일 운영이 필요 없음 | Google 계정이 없는 사람은 이용할 수 없음 |

일회용 링크도 세션은 유지할 수 있다. 차이는 세션 만료 후 재로그인에 있다. 선택된 방식은 평소 `이메일 + 비밀번호`로 로그인하고 메일은 가입 확인과 비밀번호 분실 시에만 사용한다.

## 2. 추천 가입·로그인 흐름

1. 가입 화면에서 표시 이름·이메일을 입력하면 인증번호를 보낸다. 이 단계에서는 비밀번호를 설정할 수 없다.
2. 원래 화면에서 번호를 확인한 뒤 비밀번호를 설정하면 계정이 활성화된다. 설정 완료 전에는 로그인·공간·거래 API를 사용할 수 없다.
3. 이후 로그인 화면에서 이메일과 비밀번호를 입력한다. 서버가 일치 여부를 검증하고 세션을 만든다.
4. 로그인 후 공간이 없으면 `공간 추가`, 공간이 있으면 홈으로 이동한다.
5. 비밀번호를 잊으면 이메일로 일회용 인증번호를 보내고 원래 화면에서 번호 확인·새 비밀번호 설정을 진행한다. 완료 후 기존 로그인 세션을 무효화한다.

이메일 주소는 로그인 주소로 사용하지만 내부 사용자 ID는 별도 UUID로 유지한다. 향후 Google 로그인을 추가하더라도 이메일이 같다는 이유만으로 계정을 자동 연결하지 않는다. 이메일 변경과 다른 로그인 수단 연결은 재인증 절차가 포함된 별도 정책으로 다룬다.

### 2.1 가입·비밀번호 상세 추천값

| 항목 | 추천값 | 이유 |
|---|---|---|
| 가입·재설정 인증번호 | 숫자 8자리, 10분, 일회용, 실패 최대 5회 | 원래 앱에서 확인하며 추측 시도 제한 |
| 번호 확인 후 비밀번호 설정 권한 | 10분, 일회용, 서버 해시·클라이언트 메모리만 사용 | 번호 확인과 실제 비밀번호 저장을 분리 |
| 비밀번호 | 최소 8자, 문자와 숫자를 각각 1개 이상 포함. 특수문자 선택, 공백·붙여넣기·비밀번호 관리자 허용 | 가입 시 입력 부담을 줄임 |
| 취약 비밀번호 | 흔한 비밀번호·유출 비밀번호 차단 | 형식 조건을 만족해도 예측 가능한 비밀번호 사용 방지 |
| 비밀번호 변경 | 사용자 요청이나 침해 징후가 있을 때 | 주기적인 강제 변경은 하지 않음 |

문자는 영문·한글 등 글자를 뜻하며 숫자는 숫자 문자를 뜻한다. 가입과 비밀번호 재설정에 같은 규칙을 적용한다. 특수문자 포함, 대소문자 혼합과 주기적인 변경은 요구하지 않는다. 이 기준은 단일 인증 수단에 최소 15자를 권고하는 NIST 지침보다 낮으므로 흔한·유출 비밀번호 차단과 로그인 시도 제한을 함께 적용한다.

로그인·가입·재설정 화면은 입력값을 잃지 않는 오류 안내를 제공한다. 로그인 실패 문구는 계정의 존재 여부를 드러내지 않는다. 가입 확인 링크를 다시 보내도 이전 링크는 재사용할 수 없게 한다.

## 3. 세션과 권한 경계

- 브라우저는 서버 세션 쿠키로 로그인 상태를 유지한다. 브라우저를 닫았다 다시 열어도 유지되는 지속 쿠키를 제안한다. 인증 토큰과 세션 ID를 `localStorage` 또는 `sessionStorage`에 넣지 않는다.
- 운영 환경의 쿠키는 `Secure`, `HttpOnly`, `SameSite`와 HTTPS를 적용하고, 쿠키를 쓰는 변경 요청에는 CSRF 방어를 유지한다. 초대 링크로 외부 사이트에서 진입하는 흐름을 고려해 정확한 `SameSite` 값은 구현 검증으로 정한다.
- 로그인 성공 시 세션 ID를 갱신하고 로그아웃 시 서버 세션을 무효화한다. 민감한 응답은 공유 캐시에 저장하지 않는다.
- API는 세션에서 내부 사용자 ID를 확정한 다음 활성 공간 멤버십과 각 자원의 권한을 검사한다. 요청 본문의 사용자 ID나 공간 ID만으로 권한을 주지 않는다.
- 다른 멤버의 개인 거래는 목록·상세·합계 모두 서버에서 제외한다.
- 세션은 서버에서 미사용 7일 또는 로그인 후 최대 30일 중 먼저 도달하는 시점에 만료하는 안을 제안한다. 브라우저 쿠키만 남아 있어도 서버에서 만료된 세션은 사용할 수 없다.
- PostgreSQL을 사용하는 Spring Session JDBC를 우선 검토해 서버 재시작 후에도 로그인 상태가 유지되게 한다. 세션 저장 테이블은 Flyway로 관리하고 실제 Boot 버전에서 호환성을 확인한다.
- 같은 브라우저에서 매번 비밀번호를 입력하지 않게 한다. 동시 로그인 기기 제한은 외부 테스트 전 확정한다.

## 4. 초대 수락과 계정 복구

- 로그인 전 초대 링크를 열면 로그인 완료 후 같은 초대 확인 화면으로 돌아온다. URL의 초대 원문은 로그·분석 이벤트·브라우저 저장소에 기록하지 않는다.
- 초대 확인 화면은 초대한 사람과 공간을 보여준 뒤 수락을 별도 행동으로 받는다. 로그인만으로 자동 수락하지 않는다.
- 이미 다른 활성 공간에 속한 사용자, 만료·취소·사용된 초대에는 수락을 허용하지 않는다.
- 가입 확인 메일을 받지 못하면 제한된 횟수 안에서 재발송할 수 있다. 확인 전 계정은 로그인되지 않는다.
- 비밀번호 분실 요청은 계정 존재 여부를 드러내지 않는 동일한 응답을 보낸다. 재설정 링크는 예측 불가능하고 만료·일회용이며 재사용할 수 없다.
- 이메일 계정에도 접근할 수 없다면 초기 MVP에서는 비밀번호를 복구할 수 없다. 다른 이메일을 입력했다는 이유만으로 기존 금융 기록을 이전하지 않는다.
- 다른 로그인 수단이나 이메일 변경을 추가할 때는 기존 세션에서 재인증한 사용자만 연결할 수 있게 별도 정책을 승인한다. 관리자 임의 연결 절차는 이번 초안에 포함하지 않는다.

## 5. 데이터와 운영 영향

- 기존 `users`의 내부 UUID는 유지한다. 자체 로그인 자격 증명에는 중복되지 않는 로그인 이메일 비교 키, 비밀번호 해시, 이메일 확인 시각이 필요하다. `auth_identities`는 미래의 외부 로그인 연결 경계로 둔다. 테이블·제약과 미결정 사항은 [인증 스키마 초안](../01-plan/auth-schema.md)에서 검토한다. 해당 인증 기능의 migration을 만들 때 그 기능에 필요한 정책만 먼저 확정한다.
- 비밀번호는 평문·복호화 가능한 암호문·빠른 일반 해시로 저장하지 않는다. Spring Security `PasswordEncoder`의 적응형 단방향 해시를 사용하고 실제 서버에서 비용 값을 검증한다.
- 메일 발송 자격 증명과 세션 비밀은 서버 환경에서만 관리한다. 코드, Git, 브라우저 번들, 로그에 넣지 않는다.
- 가입 확인·비밀번호 재설정 링크는 짧게 만료하고 한 번 사용하면 무효화한다. 발급·검증 횟수와 로그인 실패 시도를 제한하고 토큰 원문·비밀번호를 로그에 남기지 않는다. 발송 주소와 링크 도메인은 서버 설정으로 고정한다.
- 계정 탈퇴·데이터 삭제는 `SERVICE_PLAN.md`의 서버·로컬 데이터 정리 요구사항을 따른다. 공동 공간의 다른 멤버 데이터 보존과 소유권 이전은 별도 정책이 필요하므로 이 초안으로 삭제 동작을 확정하지 않는다.
- 메일 발송 서비스의 비용과 송신 도메인·전달 가능 여부는 실제 외부 테스트 전에 확인한다. 로컬 개발에는 실제 사용자 메일을 보내지 않는 테스트용 메일 수신기를 사용한다.
- 개발 환경은 Spring Boot `JavaMailSender`를 로컬 Mailpit SMTP에 연결하는 안을 추천한다. 운영 SMTP 제공자는 외부 테스트 준비 시 선택하고 자격 증명을 서버 설정으로 분리한다. 가입 확인·비밀번호 재설정 메일은 제품 알림 메일 비목표와 별개의 필수 인증 메일이다.

## 6. 승인 후 검증할 시나리오

- 가입은 내부 사용자 하나를 만들고 공간은 만들지 않는다. 이메일 확인 전의 업무 API 요청은 실패한다.
- 올바른 비밀번호는 로그인에 성공하고, 잘못된 비밀번호와 과도한 시도는 안전하게 거부한다.
- 만료·재사용·잘못된 확인·재설정 링크는 실패한다. 재설정 후 예전 비밀번호와 세션은 사용할 수 없다.
- 미사용 7일·최대 30일을 지난 세션이 서버에서 거부되고, 서버 재시작 후 만료 전 세션은 유지되는지 검증한다.
- 8자 미만, 문자가 없거나 숫자가 없는 비밀번호를 거부하고 특수문자 없는 유효한 비밀번호는 허용하는지 검증한다.
- 흔한·유출 비밀번호 차단, 붙여넣기와 비밀번호 관리자 자동 입력이 정상 동작하는지 검증한다.
- 비밀번호 분실 요청 응답으로 이메일 주소의 가입 여부를 구분할 수 없다.
- 인증되지 않은 API 요청, 다른 공간 자원 요청, 다른 멤버의 개인 거래 요청을 차단한다.
- 외부 초대 링크 진입 → 로그인 → 초대 정보 확인 → 명시적 수락 순서가 유지된다.
- 로그아웃 후 이전 세션 쿠키로 API에 접근할 수 없다.
- CSRF 토큰이 없는 변경 요청은 거부되고, 정상적인 브라우저 흐름은 통과한다.
- Windows Chrome·Edge와 실제 iPhone Safari에서 가입 확인, 로그인, 브라우저 재시작 후 세션 유지, 로그아웃, 비밀번호 재설정, 초대 복귀를 확인한다.

## 9. 2026-10-26 구현 결정

- 가입 때 표시 이름을 함께 받는다. 이메일은 ASCII 형식, 앞뒤 공백 제거, 전체 대소문자 구분 없이 비교한다. 원본 주소는 발송용으로 보존하고 점·+별칭을 제거하지 않는다. 국제화 이메일 원문은 지원하지 않는다.
- 비밀번호는 Spring Security의 `{pbkdf2@SpringSecurity_v5_8}` 식별자를 포함한 PBKDF2 해시로 저장한다. 흔한 비밀번호 목록과 Pwned Passwords의 해시 앞 5자리 조회를 함께 사용한다. 비밀번호 원문·전체 해시는 외부로 보내지 않는다. 확인 서비스 장애 시 가입·비밀번호 변경은 503으로 재시도하도록 한다.
- 확인·재설정 링크의 난수 원문은 메일에만 전달하고 DB에는 SHA-256 지문을 저장한다. 사용·폐기·만료 시각에서 7일이 지난 행은 시간 단위 작업으로 삭제한다.
- Spring Session JDBC와 HttpOnly 세션 쿠키를 사용한다. 미사용 7일, 최초 로그인 후 절대 30일, 로그아웃 시 세션 무효화, 비밀번호 재설정 시 자격 증명 버전 증가로 기존 모든 세션을 거부한다. 운영 쿠키는 Secure 기본값이며 local 프로필만 HTTP를 허용한다.
- 변경 요청은 Spring Security의 CSRF 쿠키와 헤더를 함께 검증한다. 웹 API 클라이언트는 CSRF 헤더를 전달하고 프록시는 여러 Set-Cookie 헤더를 각각 보존한다.
- 로그인은 이메일별 15분에 10회, 가입은 5회, 메일 재발송·복구는 합쳐서 3회 제한한다. IP별 300회 제한은 로컬 프록시 경유 사용자가 같은 주소로 보이는 점을 고려한 기본값이다. 외부 서비스 공개 전 신뢰할 수 있는 프록시의 실제 클라이언트 IP 정책을 추가한다. IP·이메일 대신 해시를 저장하고 1일 지난 카운터를 삭제한다.
- 가입은 공간을 자동 생성하지 않는다. 로그인 후 공간이 없으면 사용자가 이름을 입력해 개인 공간을 만들고 기본 분류·현금을 준비한다.
- 로컬 admin 자동 로그인은 제거했다. 사용자의 요청으로 기존 기록을 연결할 때는 `scripts/connect-local-account.ps1`에서 지정한 이메일을 서버 프로세스 메모리에만 전달한다. 해당 이메일의 최초 확인 시 자격 증명만 기존 admin 사용자로 연결하며 거래·공간·소유자 UUID는 변경하지 않는다. 이미 연결된 admin은 덮어쓰지 않고, 지정 이메일 외의 계정은 기존 기록에 접근하지 못한다. 운영 프로필에서는 이 연결을 수행하지 않는다.
- 개발 메일은 Mailpit(localhost:8025)에만 전달한다. 실제 이메일 소유 확인은 운영 SMTP 제공자를 설정한 환경에서 수행해야 한다. 동시 기기 제한 없이 각 세션의 만료·무효화 정책을 적용한다. 계정 탈퇴·이메일 변경·소셜 연동·초대 수락은 이번 구현 범위 밖이다.

### 실제 SMTP 연결 (2026-10-26)

도메인·배포 주소가 없는 현재는 사용자 선택에 따라 Gmail SMTP를 먼저 연결했다. 개발 메일은 Mailpit 기본 모드와 명시적인 `local,mail-smtp` 모드로 나뉘며, 현재 실행 API는 실제 SMTP를 사용한다. 실제 테스트 메일의 수신을 확인했다. 프로세스 재시작·키 처리·운영 전환은 [인증 메일 발송 설정](transactional-email.md)을 따른다. 운영 도메인·HTTPS 사이트·전용 발송 계정 인증은 배포 시 진행한다.

### 신규 가입 재시도 보완 (2026-10-26)

이메일 확인 전 같은 주소로 다시 가입하면 마지막으로 입력한 표시 이름·비밀번호를 새 확인 링크와 함께 적용한다. 앞서 발급한 링크는 폐기하며, 메일 발송에 실패하면 변경을 되돌린다. 이메일 확인을 마친 계정은 공개 가입 요청으로 이름·비밀번호를 변경하지 않는다. 비밀번호 변경은 재설정 절차로만 수행한다. 이 정책을 API 회귀 테스트와 실제 브라우저·SMTP 통합 검사로 검증했다.

### 회원코드 공유 연결 (2026-10-26)

초대 링크 후속 범위 대신 회원코드 요청·수락 흐름을 구현했다. 가입 시 이메일 확인을 마친 활성 로그인 계정끼리 요청할 수 있고 추가 이메일 인증은 요구하지 않는다. 회원코드만 알아서는 기록을 조회하거나 연결할 수 없으며, 받은 계정의 명시적 수락과 CSRF 검증을 요구한다. 조회·발송·재발급 제한은 실패 응답에서도 누적된다. 공유 경계·기존 기록 보존은 `SERVICE_PLAN.md` 1.1.4와 [회원코드 공유 구현](../03-analysis/member-code-sharing.md)을 따른다.
