# 한달살림 MVP 인증·계정 복구 정책 초안

> 상태: Draft — 사용자 승인 전 구현 기준으로 사용하지 않음
>
> 기준: `SERVICE_PLAN.md` 0.7, `docs/01-plan/schema.md`
>
> 범위: 가입·로그인, 세션, 초대 수락 시 사용자 식별, 로그아웃, 계정 접근 복구

## 1. 이번에 결정할 내용

제품 데이터는 서버의 사용자·공간 멤버십을 기준으로 보호한다. 로그인 방법은 아직 승인되지 않았다. 아래 추천안은 Google 계정 없이 사용할 수 있으면서 앱 비밀번호·재설정 절차를 줄이기 위한 제안이다.

| 선택지 | 장점 | 주의할 점 |
|---|---|---|
| A. 이메일 일회용 로그인 링크 (추천) | 이메일 주소만으로 가입·로그인하며 앱 비밀번호와 비밀번호 재설정 화면이 필요 없음 | 메일 발송 서비스가 필요하고 메일 지연·장애 때 로그인이 불가능함 |
| B. Google 로그인만 제공 | 별도 로그인 메일 발송이 필요 없음 | Google 계정이 없는 사람은 이용할 수 없음 |
| C. 자체 이메일·비밀번호 | 외부 로그인 제공자 없이 로그인 가능 | 비밀번호 보관, 이메일 인증, 재설정 메일 발송·남용 방지까지 직접 운영해야 함 |

추천 흐름은 `이메일 입력 → 로그인 링크 수신 → 링크 열기`다. Spring Security의 One-Time Token Login을 사용하되 이메일 전달은 앱이 메일 발송 서비스와 연결해야 한다. 이메일 인증이 가입과 로그인에 함께 쓰이며 Google Cloud OAuth 설정은 필요하지 않다.

## 2. 추천 가입·로그인 흐름

1. 사용자가 이메일 주소를 입력하고 로그인 링크를 요청한다. 가입과 로그인을 별도 화면으로 나누지 않는다.
2. 서버가 예측할 수 없는 일회용 토큰을 만들고, 등록 여부를 드러내지 않는 응답을 보낸다. 메일에는 짧은 유효기간의 HTTPS 로그인 링크를 담는다.
3. 사용자가 링크를 열면 서버가 토큰의 만료·일회용 사용 여부를 확인한다.
4. 해당 이메일의 식별자가 없으면 내부 `users`와 이메일 로그인 식별자를 원자적으로 생성한다. 이때 공간은 자동 생성하지 않는다.
5. 로그인 후 공간이 없으면 `공간 추가`, 공간이 있으면 홈으로 이동한다. 만료된 링크에는 재발송 행동을 제공한다.

이메일 주소는 로그인 주소로 사용하지만 내부 사용자 ID는 별도 UUID로 유지한다. 향후 Google 로그인을 추가하더라도 이메일이 같다는 이유만으로 계정을 자동 연결하지 않는다. 이메일 변경과 다른 로그인 수단 연결은 재인증 절차가 포함된 별도 정책으로 다룬다.

## 3. 세션과 권한 경계

- 브라우저는 서버 세션 쿠키로 로그인 상태를 유지한다. 인증 토큰과 세션 ID를 `localStorage` 또는 `sessionStorage`에 넣지 않는다.
- 운영 환경의 쿠키는 `Secure`, `HttpOnly`, `SameSite`와 HTTPS를 적용하고, 쿠키를 쓰는 변경 요청에는 CSRF 방어를 유지한다. 초대 링크로 외부 사이트에서 진입하는 흐름을 고려해 정확한 `SameSite` 값은 구현 검증으로 정한다.
- 로그인 성공 시 세션 ID를 갱신하고 로그아웃 시 서버 세션을 무효화한다. 민감한 응답은 공유 캐시에 저장하지 않는다.
- API는 세션에서 내부 사용자 ID를 확정한 다음 활성 공간 멤버십과 각 자원의 권한을 검사한다. 요청 본문의 사용자 ID나 공간 ID만으로 권한을 주지 않는다.
- 다른 멤버의 개인 거래는 목록·상세·합계 모두 서버에서 제외한다.
- 세션 지속 시간과 동시 로그인 기기 제한은 사용성 테스트 후 확정한다.

## 4. 초대 수락과 계정 복구

- 로그인 전 초대 링크를 열면 로그인 완료 후 같은 초대 확인 화면으로 돌아온다. URL의 초대 원문은 로그·분석 이벤트·브라우저 저장소에 기록하지 않는다.
- 초대 확인 화면은 초대한 사람과 공간을 보여준 뒤 수락을 별도 행동으로 받는다. 로그인만으로 자동 수락하지 않는다.
- 이미 다른 활성 공간에 속한 사용자, 만료·취소·사용된 초대에는 수락을 허용하지 않는다.
- 링크를 받지 못하면 주소를 확인하고 제한된 횟수 안에서 재발송할 수 있다. 메일 발송 장애는 로그인 장애로 표시한다.
- 이메일 계정에 접근할 수 없으면 초기 MVP에서는 계정 접근을 복구할 수 없다. 다른 이메일을 입력했다는 이유만으로 기존 금융 기록을 이전하지 않는다.
- 다른 로그인 수단이나 이메일 변경을 추가할 때는 기존 세션에서 재인증한 사용자만 연결할 수 있게 별도 정책을 승인한다. 관리자 임의 연결 절차는 이번 초안에 포함하지 않는다.

## 5. 데이터와 운영 영향

- `auth_identities`의 `(issuer, subject)` 유일성을 유지한다. 이메일 로그인 식별자는 검증된 주소를 일관되게 정규화해 관리하고, 사용자 생성과 연결을 한 트랜잭션으로 처리한다. 현재 스키마가 `issuer`를 외부 발급자로 설명하므로 이 방식을 승인하면 앱 발급 이메일 식별자도 포함하도록 정의를 갱신한다. 이메일 변경은 최초 범위에 포함하지 않는다.
- 메일 발송 자격 증명과 세션 비밀은 서버 환경에서만 관리한다. 코드, Git, 브라우저 번들, 로그에 넣지 않는다.
- 일회용 링크는 짧게 만료하고 한 번 사용하면 무효화한다. 발급·검증 횟수를 제한하고 토큰 원문을 로그에 남기지 않는다. 발송 주소와 링크 도메인은 서버 설정으로 고정한다.
- 계정 탈퇴·데이터 삭제는 `SERVICE_PLAN.md`의 서버·로컬 데이터 정리 요구사항을 따른다. 공동 공간의 다른 멤버 데이터 보존과 소유권 이전은 별도 정책이 필요하므로 이 초안으로 삭제 동작을 확정하지 않는다.
- 메일 발송 서비스의 비용과 송신 도메인·전달 가능 여부는 실제 외부 테스트 전에 확인한다. 로컬 개발에는 실제 사용자 메일을 보내지 않는 테스트용 메일 수신기를 사용한다.

## 6. 승인 후 검증할 시나리오

- 첫 유효 링크 로그인은 내부 사용자 하나를 만들고 공간은 만들지 않는다. 재로그인은 같은 사용자로 연결된다.
- 만료·재사용·잘못된 링크와 발급·검증 횟수 초과는 로그인에 실패한다.
- 이메일 주소가 존재하는지 요청 응답으로 구분할 수 없고, 메일 발송 실패를 안전하게 처리한다.
- 인증되지 않은 API 요청, 다른 공간 자원 요청, 다른 멤버의 개인 거래 요청을 차단한다.
- 외부 초대 링크 진입 → 로그인 → 초대 정보 확인 → 명시적 수락 순서가 유지된다.
- 로그아웃 후 이전 세션 쿠키로 API에 접근할 수 없다.
- CSRF 토큰이 없는 변경 요청은 거부되고, 정상적인 브라우저 흐름은 통과한다.
- Windows Chrome·Edge와 실제 iPhone Safari에서 링크 수신, 로그인, 세션 유지, 로그아웃, 초대 복귀를 확인한다.

## 7. 승인 대기 결정

| ID | 결정 | 추천안 |
|---|---|---|
| AUTH-01 | MVP 로그인 수단 | 이메일 일회용 로그인 링크만 제공 |
| AUTH-02 | 앱 자체 비밀번호·재설정 | MVP에서 운영하지 않음. 이메일 접근을 로그인 근거로 사용 |
| AUTH-03 | 향후 다른 로그인 수단의 동일 이메일 자동 연결 | 허용하지 않음 |
| AUTH-04 | 초대 링크 로그인 후 처리 | 초대 확인 화면으로 복귀하고 사용자가 직접 수락 |

메일 발송 서비스, 세션 지속 시간, 동시 기기 제한, 공동 공간의 계정 탈퇴·삭제 정책은 이 네 결정 이후 별도로 확정한다.
