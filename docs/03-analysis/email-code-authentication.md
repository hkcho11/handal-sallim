# 앱 안에서 이메일 인증번호 확인

기준일: 2026-10-28. 현재 이메일·비밀번호 계정을 유지하면서 가입 확인과 비밀번호 재설정을 메일 URL 대신 원래 앱에서 번호를 입력하는 방식으로 변경한다.

## 사용자 흐름

1. 가입은 표시 이름·이메일, 비밀번호 찾기는 이메일을 입력한다.
2. 메일로 온 숫자 8자리를 원래 한달살림 화면에 입력한다. 홈 화면 웹 앱과 Safari 간에 인증 상태나 쿠키를 전달하지 않는다.
3. 번호가 확인되면 같은 화면에서 비밀번호·확인을 입력한다. 가입 또는 재설정 완료 후 로그인한다. 번호 확인만으로 로그인하거나 금융 API 권한을 주지 않는다.
4. 번호 재발급과 이메일 변경을 제공한다. 숫자 키패드·one-time-code 자동완성 힌트·붙여넣기·앞자리 0을 지원하고 단계 전환 시 입력칸에 초점을 옮긴다. 자동완성 실제 동작은 OS·메일 앱 지원에 따른다.

## 서버와 보안

- V14 `email_auth_codes`에 요청 ID·사용자·목적·적응형 해시·실패 횟수·만료·사용·폐기 시각을 저장한다. 번호는 SecureRandom으로 발급하고 10분·일회용·최대 5회 실패를 적용한다.
- 번호가 짧으므로 단순 SHA-256 대신 요청 ID·목적을 포함한 salt 기반 PBKDF2로 저장한다. 요청 ID만으로는 인증할 수 없으며 다른 요청·목적의 번호는 사용하지 못한다.
- 번호 확인 오류에서도 실패 횟수는 커밋한다. 자격 증명 → 번호 순서로 잠가 같은 번호를 동시에 확인해도 하나만 성공한다.
- 확인 성공 시 비밀번호 설정만 허용하는 256비트 무작위 일회용 권한을 반환한다. 이 권한은 10분 유효하고 기존 `auth_action_tokens`에 SHA-256 해시로 저장한다. 이후 비밀번호와 권한을 검증해 기존 가입 완료·재설정 트랜잭션을 사용한다.
- 번호와 설정 권한의 수명은 각각 10분이다. 번호가 만료되기 직전에 확인한 경우에도 설정 단계에 10분을 부여한다. 비밀번호 검증 실패는 설정 권한을 소모하지 않는다.
- 재발급은 이전 번호·미사용 설정 권한을 폐기한다. SMTP 실패 시 롤백하여 이전 번호·권한을 유지한다. 이메일별 발급 제한은 기존 가입 5회, 재발송·복구 합산 3회/15분을 유지한다. 확인 API에는 요청별 5회 실패와 IP별 보조 제한이 있다.
- 부적격·미존재 계정에도 같은 모양의 응답과 무작위 요청 ID를 반환한다. 그 ID에 대한 인증은 실패한다. 발송 여부에 따른 응답 시간 차이를 제거한 것으로 주장하지 않는다.
- CSRF, 기존 사용자 ID·비밀번호·세션, 비밀번호 변경 뒤 모든 기존 세션 거부, 공유 권한은 유지한다. 코드·사용자명·설정 권한 원문을 로그에 기록하지 않는다.
- 사용·폐기·만료된 코드 행은 기존 토큰과 마찬가지로 7일 뒤 정리한다. 로컬 admin 자격 증명 연결 시 코드 FK도 함께 이전한다.

## 앱 복귀·새로고침·오류

- 원래 탭의 sessionStorage에는 요청 ID·이메일 초안·진행 단계만 보관한다. 번호·비밀번호·설정 권한·세션 ID는 저장하지 않는다. 완료·이메일 변경 시 초안을 지운다.
- 번호 입력 단계에서 새로고침해도 같은 요청을 이어간다. 앱 시작이 로그인 화면으로 돌아간 경우 진행 중인 가입·재설정 링크로 복귀할 수 있다. 별도 브라우저나 새 탭으로 초안을 공유하지 않는다.
- 번호 확인 후 새로고침하면 메모리의 설정 권한이 사라지므로 새 번호를 받도록 안내한다. 번호 확인 성공 응답이 유실된 경우에도 새 번호를 요청한다. 서버는 이미 사용한 번호를 재사용하게 하거나 원문 권한을 복구해 반환하지 않는다.
- 브라우저가 탭 저장소까지 삭제한 경우에는 이메일을 다시 입력해 번호를 새로 요청한다. 모든 OS 상태에서 진행 상태가 보존된다고 보장하지 않는다.
- 기존 메일 링크는 원래 만료시간까지 수용한다. 새 메일에는 URL을 넣지 않으며 새 번호 발급 시 기존 링크도 폐기한다. 기존 링크 화면의 수동 홈 화면 복귀 안내는 호환 경로에만 남긴다.
- 실제 아이폰·홈 화면 앱·Gmail 수신 검증은 별도로 필요하다. Windows의 Chromium 검사는 같은 화면의 HTTP 흐름·저장 상태·화면 크기·확대를 검증하는 것이며 iOS 자체 동작의 검증을 대체하지 않는다.

설계 참고: [OWASP 계정 복구 지침](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). 구체적인 8자리·10분·5회는 이 프로젝트의 구현 기본값이다.

## 검증 결과

실제 사용자 DB에서 임의 금융 기록을 만들거나 Gmail로 테스트 메일을 발송하지 않았다. 현재 계정의 비밀번호도 임의로 변경하지 않았다.

- API `spotlessCheck test build`: 95건 통과, 실패·오류·skip 0. 5회 실패 영속화, 4회 실패 후 성공, 요청·목적 구분, 10분 만료, 설정 권한 재발급·만료, 동시 확인 단일 성공, 발송 실패 시 이전 번호 유지, 미존재 계정 일반 응답, CSRF, admin 연결 FK, 기존 금융 기능 포함.
- 웹 format:check·lint·typecheck·build 통과. Vitest 전체 96건 통과.
- 화면 Playwright `e2e/auth.spec.ts e2e/email-code.spec.ts`: 9건 통과. 360/1280px, 숫자·공백 포함 붙여넣기·앞자리 0, 입력 초점, 번호 입력 단계 새로고침, 로그인 화면에서 진행 중인 인증 재개, 설정 권한을 저장소에 보관하지 않음, 설정 단계 새로고침 안내, 재발급·이메일 변경, 구버전 링크, 200% 확대 시 가로 넘침을 확인했다. 모바일 캡처를 직접 확인했다.
- 실제 격리 통합 `scripts/test-auth-flow.ps1 -SkipBuild`: 5건 통과 (47.5초). SMTP로 온 메일에 URL이 없고 8자리 번호가 있는지 검사하며 원래 화면에서 번호 입력·비밀번호 설정·로그인, 재가입 비밀번호 주입 거부, SMTP 중단·복구, 이전·사용 번호 거부, 앱 안에서 재설정·기존 세션 거부, 회원코드 공유·보존·연결 해제까지 확인했다.
- 초기 화면 검사에서 번호 입력칸의 설명이 접근성 이름에 섞여 정확한 label 선택이 실패했다. aria-label과 설명 연결을 분리해 수정했다. 구버전 화면을 쓰던 통합 실행은 중단하고 하네스 정리 후 새 빌드로 다시 실행했다. 브라우저 초기화도 취소 가능한 hydration 이후 복원으로 조정해 린트와 화면 검사를 재확인했다.
- `git -c core.safecrlf=false diff --check`: 통과.
- 실제 iPhone Safari·홈 화면 설치 앱·실제 Gmail 인증번호 수신, 운영 인프라 검증은 이번에 실행하지 않았다.

## 남은 범위

실제 운영 HTTPS·도메인, 신뢰할 프록시에서의 IP 식별, Next.js 보안 버전, 웹 보안 헤더, 비밀번호 해시 비용 강화는 기존 후속 항목이다. 인증번호 도입이 기존 보안 점검 전체를 완료하는 것은 아니다.
