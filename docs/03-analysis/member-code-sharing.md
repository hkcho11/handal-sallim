# 회원코드 공유 연결 구현

기준일: 2026-10-26. 브랜치: `feature/email-password-auth`.

## 사용자 흐름

설정 → 함께 쓰기에서 내 회원코드를 확인한다. 요청하는 사람은 상대의 코드 입력 → 이름·코드 확인 → 함께 쓰기 요청, 받은 사람은 새로고침 → 요청 확인 → 상대 이름·코드·공유 범위 확인 → 수락한다. 로그인과 가입 시 이메일 확인은 기존 인증을 사용하며 연결 때 별도 이메일 인증을 요구하지 않는다.

- 회원코드는 무작위 영문·숫자 8자리이며 표시할 때 하이픈을 넣는다. 입력은 대소문자·공백·하이픈을 무시한다. 0/O·1/I는 생성하지 않는다.
- DB 기본키와 사용자별 활성 코드 고유 제약으로 중복을 막고 충돌 시 재생성한다. 폐기된 코드는 재사용하지 않는다.
- 24시간 대기 요청, 요청 취소·거절·코드 재발급을 제공한다. 재발급 시 이전 코드와 받은 대기 요청이 취소된다.
- 본인 요청·미인증/비활성 사용자·이미 공유 중인 계정·권한 없는 수락을 차단한다. 반대 방향의 대기 요청은 받은 요청을 확인하도록 안내한다.
- 푸시·요청 도착 배너·주기적 조회·실시간 통신을 추가하지 않았다. 처음 화면에 들어갈 때와 새로고침 버튼을 누를 때 상태를 조회한다.

## 공유 경계와 보존

- 수락 트랜잭션에서 새 SHARED 공간을 생성하고 두 계정을 활성 멤버로 등록한다. 같은 요청을 다시 수락해도 기존 연결을 반환하며 동시 경쟁에서도 한 연결만 성립한다.
- 기존 SOLO 공간은 ARCHIVED, 기존 멤버십은 LEFT로 보존한다. 사용자·거래·공간·작성자·소유자의 기존 FK는 변경하거나 삭제하지 않는다.
- `private_space_archives`가 인증된 원래 사용자에게만 이전 기록의 읽기 권한을 준다. 별도 보존 화면에서 수입·저축·결제 내역·반복 설정과 본인 작성 기존 거래를 확인하며 편집할 수 없다.
- 보관 공간의 금융 테이블 INSERT/UPDATE/DELETE를 DB 트리거로 보호해 수락과 겹친 쓰기가 과거 기록을 덮어쓰지 못하게 한다.
- 새 수입·지출·저축은 새 공유 공간에 등록된다. 기록한 월·발생일이 과거여도 연결 후 새로 등록한 기록이면 공유한다. 공유 기준을 거래 날짜로 판정하지 않는다.
- 수입·저축 잔액·완료 거래·기존 예정 청구를 자동 이월하지 않는다. 기존 활성 반복 고정비의 설정만 새 식별자로 이어받으며 공유 시작일 이후이고 마지막 완료 회차보다 뒤인 첫 회차를 만든다. 미정 일정은 미정으로 유지한다. 선납 완료한 미래 회차를 다시 미결제로 만들지 않는다.
- 이어받는 설정에 참조된 분류·세부 분류·활성 결제수단을 새 공간에 매핑한다. 이름이 비슷한 두 고정비를 자동으로 합치거나 삭제하지 않는다. 수락 화면에서 중복 비용은 연결 후 정리하도록 안내한다.
- 제거했던 개인 지출 API는 인증 후에도 접근을 거부한다. 보존된 과거 데이터는 삭제하지 않고, 새 비공유 개인 지출이 생성되는 우회 경로를 차단했다.

## 구조

- migration: `V10__member_code_sharing.sql`.
- API: `GET /api/sharing`, `POST /lookup`, `POST /requests`, `POST /requests/{id}`, `POST /member-code`, `GET /archives` (나머지는 `/api/sharing` 기준).
- 계층: sharing.api → sharing.application → sharing.domain / persistence. 기존 고정비 생성 유스케이스를 사용해 앞으로의 설정을 생성한다.
- 조회·요청·재발급 횟수 제한은 실패 응답에서도 누적되게 트랜잭션 밖에서 적용한다. 수락은 양쪽 사용자 행을 UUID 순으로 잠그고 현재 연결·개인 공간을 재검증한다.
- local 테스트 데이터 준비는 이미 보관된 admin 공간에 새 금융 설정을 삽입하지 않는다.

## 검증

- API Spotless·테스트·빌드: 74개 테스트 성공. 공유 테스트는 코드 정규화·접근 권한·CSRF·중복/역방향 요청·거절·취소·만료·재발급·실패 요청 제한·동시 수락·재수락·새 공간 없는 사용자·이전 기록 격리·새 수입/저축 공유·반복 회차 이관·미래 선납 중복 방지를 포함한다.
- 제거된 개인 지출 API는 실제 HTTP와 로그인 세션으로 조회·생성이 거부되고 거래가 늘지 않는지 확인했다.
- 웹 단위 테스트: 88개 성공. 공유 응답의 경계 검증과 연결 실패·거절 안내를 추가했다.
- 기존 브라우저 회귀 검사: 37개 성공.
- 실제 DB·SMTP 연결 브라우저 검사: 5개 성공. 새 계정 두 명을 가입·메일 확인·로그인한 뒤 코드 입력·상대 확인·요청·수락·공유 시작·이전 기록의 본인 전용 보존까지 확인했다. 거래 월이 공유 시작보다 과거여도 새로 등록한 수입은 두 사람에게 공유되는지 검증했다.
- 360px·1280px 화면과 200% 확대에서 가로 넘침을 확인했고 360px 스크린샷을 검토했다. 회원코드 입력 폼의 Enter 제출도 검사한다.
- 검사 환경은 별도 PostgreSQL·Mailpit·임시 API·웹 서버이며 실제 사용자 DB와 Gmail에 시험 가입·연결 요청·메일을 만들지 않는다.

## 현재 개발 서버 반영

Gmail 연결을 유지한 채 최신 JAR로 재시작했고 실행 사본이 빌드와 일치함을 확인했다. V10 migration 적용 성공과 API 준비 상태를 확인했다. 실제 계정 간 연결은 사용자가 화면에서 상대를 확인하고 수락해야 실행된다.

## 남은 범위

실제 iPhone Safari와 원격 GitHub Actions 실행, 운영 HTTPS 도메인·SMTP의 전체 연결 흐름은 별도로 확인해야 한다. 새 검사는 기존 CI의 실제 인증 검사에 포함되어 있다. 연결 해제·상대 교체·과거 기록의 선택 공개·푸시 알림은 이번 범위가 아니다. 기존 미커밋 변경을 보존했으며 임의로 포함한 커밋·PR·병합·공개 배포는 하지 않았다.

## 후속 전 기능 공유 점검

연결된 두 계정으로 홈·수입·지출·저축·결제수단·분류의 교차 조회·수정·삭제와 소유자/결제자 표시를 추가 검증했다. API 전체 76개와 확장한 실제 브라우저 통합 검사 5개가 통과했다. 현재 기능의 공유 지원과 아직 구현되지 않은 전체 기획 항목은 [함께 쓰기 전체 기능 점검](shared-feature-audit.md)에 구분했다.
