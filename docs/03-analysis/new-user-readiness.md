# 신규 사용자 흐름 배포 전 점검

점검일: 2026-10-26. 브랜치: `feature/email-password-auth`.

**판정: 가입·이메일 확인·로그인·개인 공간 사용 흐름은 검증했으나, 타인 초대·공유 연결이 미구현이므로 요청한 전체 공유 서비스의 배포 준비는 끝나지 않았다.**

## 단계별 결과

| 사용자 단계 | 결과 | 근거 |
|---|---|---|
| 첫 접속 → 로그인/회원가입 진입 | 통과 | 새 브라우저에서 비인증 접속과 로그인 복귀 확인 |
| 이메일 가입 → 확인 메일 수신 | 통과 | 실제 웹·API·PostgreSQL·SMTP를 연결한 격리 검사. 다른 프로세스의 메일함에서 확인 링크 추출 |
| 이메일 확인 → 로그인 | 통과 | 링크를 별도 브라우저에서 확인, 미확인 계정 로그인 거부, 확인 후 로그인 성공 |
| 첫 개인 공간 생성 → 실제 수입 기록 | 통과 | 새 계정은 공간이 없고 명시적 생성 후 업무 API 사용 가능 |
| 다른 신규 계정과 데이터 격리 | 통과 | 두 계정이 각각 가입·확인·로그인. 상대 목록·단건 조회로 첫 사용자의 수입에 접근하지 못함 |
| 같은 브라우저에서 계정 변경 | 통과 | 로그아웃 후 다른 계정으로 로그인할 때 이전 계정의 내역이 보이지 않음 |
| 다른 사람 초대 → 확인 → 수락 → 공유 공간 이용 | 미구현 / 배포 차단 | 초대 migration·서버 API·웹 화면·로그인 후 초대 복귀가 없음. 현재 신규 계정의 온보딩은 개인 공간 생성 경로만 제공 |
| 외부 기기에서 운영 인증 링크 열기 | 미확인 / 운영 설정 필요 | 아직 보유 도메인·운영 주소가 없으며 현재 메일 링크는 localhost를 사용 |

공간과 멤버십을 기준으로 하는 데이터 구조와 일부 멤버 권한 테스트가 존재하는 것만으로 실제 초대·연동 제품 흐름이 구현됐다고 판단하지 않았다. 임의로 신규 사용자를 기존 admin이나 다른 사용자의 공간에 연결하지 않았다.

## 재현하고 수정한 오류

### 인증 전 재가입 후 새 비밀번호로 로그인 불가

- 재현: 같은 이메일로 가입 → 확인 전 비밀번호·표시 이름을 바꿔 재가입 → 새 링크 확인 → 방금 입력한 비밀번호로 로그인 시 401.
- 원인: 미확인 기존 계정에는 새 링크만 발급하고 기존 비밀번호 해시·표시 이름을 유지했다.
- 수정: 미확인 계정에 한해 마지막 가입 입력과 링크 재발급을 같은 트랜잭션으로 처리한다. 기존 링크는 폐기한다. 메일 실패 시 변경은 롤백한다. 확인 완료 계정은 가입 요청으로 변경하지 않는다.
- 검증: 수정 전 실패를 API 회귀 테스트와 실제 브라우저 흐름으로 확인했다. 수정 후 두 검사 모두 통과했다.

### 연결 장애·잘못된 게이트웨이 응답 안내

- 인증 API의 네트워크 예외나 JSON 해석 오류가 그대로 화면에 전달될 수 있었다.
- 내부 연결 세부정보 대신 한국어 재시도 문구를 표시하도록 수정하고 단위 테스트로 보호했다. 입력값은 실패 시 유지한다.

## 실패 상황 검사

- 실제 테스트 SMTP 컨테이너를 중단한 상태에서 가입 시 실패 안내와 입력 유지 확인. 복구 뒤 같은 입력 재시도로 메일 수신·확인·로그인·공간 생성 성공.
- 재발송 전 링크·이미 사용한 링크 거부, 유효한 최신 링크 성공.
- 별도 브라우저에서 비밀번호 재설정 후 기존 세션과 이전 비밀번호 거부, 새 비밀번호 로그인 성공.
- API 테스트로 만료 링크·동시 링크 소비·동시 가입·시도 제한·CSRF 누락·메일 발송 실패 롤백·세션 만료·권한 검사를 확인했다.

## 실행 결과와 재실행

- API `spotlessCheck test build`: 67개 테스트, 실패·오류 0, 빌드 성공.
- 웹 포맷·ESLint·타입 검사·단위 테스트: 성공, 단위 테스트 85개.
- 웹 프로덕션 빌드와 기존 Playwright 검사: 성공, 브라우저 테스트 37개.
- 격리된 실제 인증 브라우저 검사: 4개 통과. 별도 포트·임시 PostgreSQL·Mailpit과 API를 사용하고 응답을 가로채지 않는다. 종료 후 생성한 프로세스·컨테이너만 정리한다. 실제 사용자 DB·Gmail 설정과 메일함을 테스트 대상으로 사용하지 않는다.
- 현재 개발 API의 실행 JAR이 수정 빌드와 일치하고, Gmail 프로필과 준비 상태가 유지됨을 확인했다. 키는 숨김 입력으로 재설정했으며 추가 테스트 메일은 보내지 않았다.

```powershell
# PowerShell 7, Docker Desktop 필요. 빌드부터 수행
.\scripts\test-auth-flow.ps1
# API와 웹 빌드가 이미 최신이면
.\scripts\test-auth-flow.ps1 -SkipBuild
```

CI의 web 작업에도 Java 준비·API JAR 빌드 후 같은 인증 통합 검사를 추가했다. 이 대화에서는 Windows에서 실행했고, 변경된 GitHub Actions의 원격 Ubuntu 실행은 아직 수행하지 않았다. 기존부터의 대규모 미커밋 변경은 보존했고 임의로 커밋·PR에 포함하지 않았다.

## 배포 전에 완료할 사항

1. 공간 초대 발급·취소·재발급·24시간 만료·일회 수락과 멤버 수 검증을 구현한다. 수락은 공간·사용자 잠금과 멤버십 생성을 한 트랜잭션으로 처리한다.
2. 초대받은 사용자의 가입·메일 확인·로그인 후 같은 초대 확인 화면으로 돌아오게 한다. 개인 공간 생성을 강제하기 전에 초대 수락을 제공한다. 이미 활성 공간이 있는 사용자의 처리와 기존 기록의 공개 범위는 서비스 정책대로 명시적으로 검증한다.
3. 실제 두 사용자가 공유 공간에서 기록을 함께 조회·추가하고, 개인 거래는 다른 멤버에게 노출되지 않는 전체 흐름을 검증한다.
4. 운영 HTTPS 주소·발신 도메인/전용 발송 서비스·호스팅 비밀 설정을 준비한다. 다른 기기에서 메일 링크를 열어 가입 확인·재설정을 확인한다.
5. 실제 배포 프록시의 신뢰 경계 안에서 클라이언트 IP 처리와 시도 제한을 검증한다. 현재 Next 프록시를 거친 요청은 API에서 같은 원격 주소로 보일 수 있어 IP별 제한이 전체 사용자에게 공유될 수 있다. 임의의 브라우저 헤더를 신뢰하는 방식으로 해결하지 않는다.

테스트는 예상한 장애에서 안전한 실패·재시도를 검증한다. Gmail의 일일 한도·반송·스팸 분류·외부 서비스 장애·배포 환경별 동작까지 모두 보장하지 않는다. 비밀번호 유출 조회는 통합 테스트에서 외부 통신 없이 대체했으며, 실제 Google 받은편지함 수신은 앞선 SMTP 연결 작업에서 확인한 범위다. 실제 iPhone Safari와 운영 SMTP/호스팅에서의 전체 흐름은 추가 확인이 필요하다.

## 2026-10-26 후속 구현

이 보고서 작성 이후 회원코드 요청·수락 기반 공유 연결을 구현했다. 초대 링크 방식 대신 회원코드를 사용하며, 연결 후 새 기록 공유·기존 기록의 본인 전용 보존을 실제 두 사용자 브라우저 흐름으로 검증했다. 이전의 공유 미구현 판정은 이 후속 결과로 대체한다. 상세한 정책·검증·남은 운영 범위는 [회원코드 공유 구현](member-code-sharing.md)을 따른다.
